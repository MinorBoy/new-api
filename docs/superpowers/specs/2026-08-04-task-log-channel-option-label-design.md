# 任务日志渠道筛选选项设计

## 背景

任务日志页面已经支持按当前时间范围内全部任务日志提取渠道 ID，并通过下拉选择后自动筛选。当前渠道选项只展示数字 ID，无法直接识别渠道，需要与使用日志页面的渠道筛选交互保持一致。

## 目标

- 渠道选项展示为 `渠道 ID - 渠道名称`，例如 `23 - paipu`。
- 任务日志渠道筛选使用与使用日志页面相同的可搜索 `Combobox` 交互。
- 支持从选项中选择，也支持手动输入任意渠道 ID。
- 选择或输入后自动执行筛选，并将页码重置为第 1 页。
- 可选渠道仍只来源于当前时间范围内全部任务日志，不受分页、状态、请求模型、用户等其他筛选条件影响。

## 数据契约

管理员接口 `GET /api/task/filter-options` 的 `data.channels` 从整数数组调整为结构化数组：

```json
[
  {
    "id": 23,
    "name": "paipu"
  }
]
```

普通用户的 `GET /api/task/self/filter-options` 仍不返回渠道选项。

后端首先从当前时间范围内的任务日志去重取得渠道 ID，再使用已有的 `model.GetChannelsByIds` 批量查询渠道名称，避免逐项查询。渠道记录已删除或名称为空时，仍保留该日志渠道 ID，并返回空名称。

## 前端交互

任务日志渠道筛选复用使用日志页面的 `Combobox` 组合方式：

- `openOnFocus` 打开候选列表。
- `allowCustomValue` 允许手动输入渠道 ID。
- 选项值保持为渠道 ID 字符串，提交到任务日志接口时仍使用 `channel_id`。
- 有名称时显示 `ID - 名称`，无名称时仅显示 `ID`。
- 选择候选项或完成手动输入后，沿用任务日志现有自动查询逻辑，并重置 `page=1`。

状态、请求模型和用户筛选保持现有实现不变。

## 错误与兼容处理

- 若批量查询渠道表失败，过滤选项接口返回统一 API 错误，不返回不完整的成功响应。
- 若单个渠道不存在，接口正常返回该 ID 和空名称，前端回退显示 ID。
- 不修改已有任务日志数据，也不需要数据库迁移。
- 保持 SQLite、MySQL 和 PostgreSQL 兼容，渠道名称查询使用现有 GORM 方法。

## 测试

- 模型或控制器测试：验证当前时间范围内渠道去重、名称批量补齐及已删除渠道回退。
- 前端选项归一化测试：验证 `23 - paipu` 和缺失名称时的 `23`。
- 组件交互测试：验证渠道筛选支持搜索和自定义 ID，选择后自动导航到第 1 页。
- 完成后运行相关 Go 测试、用量日志前端测试、类型检查、涉及文件的 lint 和生产构建。
- 重建本地容器，并在桌面端和移动端浏览器验证渠道显示与自动筛选。
