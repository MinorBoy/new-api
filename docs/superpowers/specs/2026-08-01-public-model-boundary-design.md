# 公共模型边界设计

## 目标

本项目对外只提供三个 Doubao Seedance 标准模型 ID：

- `doubao-seedance-2-0-260128`
- `doubao-seedance-2-0-fast-260128`
- `doubao-seedance-2-0-mini-260615`

用户只需将现有客户端的 Base URL 和 API Key 切换到本项目，即可使用上述标准模型。上游渠道模型、渠道名称、渠道类型和实际路由目标均属于内部实现，不得通过模型广场、模型列表 API 或直接模型调用暴露给用户。

## 根因

当前 `model.GetPricing()` 和用户模型列表都从启用的 `abilities` 生成。配置导入为内部路由同时保存标准模型与上游模型，因此模型广场和 `/v1/models` 将两类模型一并公开。直接请求上游模型 ID 也会沿现有能力表完成渠道选择。

问题不是前端展示错误，而是系统缺少“公共产品模型”和“内部渠道能力”之间的统一边界。

## 模型边界

`pkg/modelrouting.CanonicalModels` 是公共模型目录的唯一代码来源。公共目录只包含上述三个精确 ID，不包含前缀匹配、模糊匹配或运行时自动发现。

以下内容继续保留为内部数据：

- `channels.models` 中的标准模型和上游模型。
- `channels.model_mapping` 中的标准模型到上游模型映射。
- `abilities` 中用于渠道选择的全部能力。
- 成本规则、路由目标、配置导入映射和历史审计中的上游模型。
- 旧 Mini 别名 `doubao-seedance-2-0-mini-260128`，仅用于内部历史兼容与规范化。

公共边界不删除或改写内部数据，只在对外读取和公共请求入口执行投影与校验。

## 对外读取

### 模型广场

`GET /api/pricing` 在完成现有分组可用性过滤后，再与公共模型目录取交集。响应必须满足：

- `data` 只包含公共模型 ID，并按公共目录顺序稳定返回。
- 正常配置下模型广场总数为 3。
- 某个公共模型没有可用渠道或计费配置时，失败关闭：该模型可以暂时不展示，但不得用上游模型补位。
- `vendors` 只返回公共模型实际引用的公开供应商信息。
- 公共供应商名称和图标固定表达 Doubao 产品身份，不随实际选中的上游渠道变化。
- `supported_endpoint` 只返回公共模型声明的端点类型所需条目。

内部 `model.GetPricing()` 继续构建完整定价与能力缓存，避免影响计费、成本核算、路由诊断和管理员功能。公共过滤在控制器边界完成，不改变内部缓存语义。

### 模型列表 API

以下用户接口均与公共模型目录取交集：

- OpenAI、Anthropic 和 Gemini 兼容的模型列表接口。
- 用户可用模型接口及依赖它的 Playground/选择器。
- 单模型查询接口。

Token 模型限制只能进一步缩小公共目录，不能把上游模型重新加入响应。`owned_by` 固定为 `doubao`，不得根据首选渠道返回实际供应商名称。

管理员渠道管理、模型元数据管理、成本核算和配置导入接口仍可查看完整内部模型集合。

## 公共请求校验

所有经过公共 Relay 路由且携带模型 ID 的新请求，在渠道选择和模型映射之前执行公共目录校验：

1. 读取客户端原始模型 ID，不先做上游映射或别名规范化。
2. 仅精确接受三个公共模型 ID。
3. 上游模型 ID、旧 Mini 别名和其他未知模型返回协议兼容的 `model_not_found` 错误。
4. 错误响应不包含渠道 ID、渠道名、候选模型或成本规则信息。
5. 通过目录校验后，继续执行现有分组权限、Token 模型限制、计费校验和利润感知路由。

任务查询、视频内容下载和 Remix 等不携带新模型选择的操作不重复校验模型目录；它们按已保存任务的公开原始模型继续授权。管理员渠道测试和内部运维接口不经过公共模型边界。

## 数据流

```text
sd收录.xlsx / 渠道配置
        |
        v
内部模型库存、abilities、映射、成本规则、路由目标
        |
        +--> 管理员与内部路由：完整可见
        |
        +--> 公共模型目录精确投影
                 |
                 +--> /api/pricing
                 +--> /v1/models 及兼容列表
                 +--> 用户模型选择接口
                 +--> 公共 Relay 请求模型校验
```

## 缓存与一致性

- 继续使用现有定价和渠道缓存失效机制。
- 公共目录为进程内不可变常量，不引入数据库表或新的配置缓存。
- 公共列表从完整缓存生成新切片，禁止原地修改共享 `pricingMap`。
- 配置导入发布后，现有缓存刷新会更新三个公共模型的可用分组、价格和端点，但不会改变公共目录成员。

## 兼容性

- 用户通过三个标准模型 ID 的现有请求保持兼容。
- 直接使用上游渠道模型 ID 的行为被有意终止，这是本次安全边界修复。
- 旧 Mini 别名不再作为公共 API 兼容别名；历史任务和内部路由仍可规范化读取。
- 不修改数据库结构，继续兼容 SQLite、MySQL 和 PostgreSQL。
- 不改变管理员查看、导入和维护上游模型的能力。

## 验证策略

后端先添加失败回归测试，再实现最小修复：

- 定价接口同时存在公共模型和上游模型时，只返回三个公共模型。
- 供应商和 `owned_by` 不泄露实际上游渠道。
- OpenAI、Anthropic、Gemini 和用户模型列表均不返回上游模型。
- Token 模型限制包含上游模型时仍不能将其公开。
- 单模型查询拒绝上游模型并允许公共模型。
- 公共 Relay 请求使用上游模型时，在渠道选择前返回 `model_not_found`。
- 三个公共模型通过校验并继续进入现有路由流程。
- 管理员内部模型接口仍返回完整模型集合。

验收时重新构建本地容器，并在浏览器确认模型广场总数为 3、三个模型名精确匹配且无上游供应商信息。随后使用 API 请求验证模型列表与直接调用边界，并运行全量 Go 测试、前端类型检查、生产构建和差异检查。
