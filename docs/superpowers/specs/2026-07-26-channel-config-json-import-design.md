# 渠道配置 Excel 转换与 JSON 导入设计

**日期：** 2026-07-26
**状态：** 已确认，待书面审阅

## 1. 背景与结论

目标文件为：

```text
C:/Users/880pro/Documents/new-api/outputs/019f9dbb-4e5d-7933-8531-d38e417ec068/渠道模型成本与利润模板-更新.xlsx
```

当前 new-api 不支持从本地 Excel 或 CSV 批量导入渠道、模型映射、成本规则、用户售价和路由策略。现有渠道批量接口只覆盖多 Key 创建、状态、删除和标签等有限操作；成本规则和路由策略分别使用自己的管理接口。原有《渠道模型成本与计费毛利润设计》也明确把 Excel/CSV 导入留作独立设计。

本需求可行，但不能把 Excel 直接翻译成数据库写入。推荐方案是：

1. 使用独立的纯前端静态转换器在浏览器本地解析 Excel；
2. 转换器输出版本化、可审计、无密钥的规范 JSON；
3. 管理员把 JSON 上传到 new-api；
4. new-api 重新校验、绑定渠道线路、生成惰性配置和差异提案；
5. 管理员解决冲突、审核并以单一事务发布；
6. 发布顺序为成本规则、用户售价、路由启用，任一步失败整体回滚。

Excel 原文件永远不上传到 new-api。JSON、导入报告、审计和日志中永远不保存 API Key、Authorization、Token 或其他凭据。

## 2. 目标

本设计交付一条完整且可恢复的配置导入链路：

- 从当前 v1 Excel 和未来 v2 Excel 生成规范 JSON；
- 在转换器中展示渠道、SKU、售价、成本、映射、路由、冲突和最终 JSON；
- 在 new-api 中分阶段完成上传、服务端校验、渠道绑定、草稿生成、审核和发布；
- 支持新增渠道、绑定已有渠道、跳过线路和拆分冲突线路；
- 为成本规则增加成本变体身份，并由路由目标确定成本变体；
- 为官方售价生成用户售价提案，默认用户组为 `default`；
- 所有新渠道、路由策略和路由目标默认禁用；
- 重复导入相同内容时保持幂等；内容变化时生成新版本或差异提案；
- 不直接更新活动成本规则、活动售价、活动路由或历史账本；
- 在 SQLite、MySQL 和 PostgreSQL 下保持相同行为。

## 3. 非目标

本期不包含：

- Excel 文件直接上传到 new-api；
- 在转换器中填写或保存 API Key；
- 从供应商网站在线抓取或同步价格；
- 自动执行 Excel 宏、公式脚本或外部数据连接；
- 根据自由文本备注静默推断可发布的路由条件；
- 无审核覆盖活动规则、售价或路由；
- 自动回算历史请求成本和历史利润；
- 使用供应商成本反推或自动决定最终用户售价；
- 在普通用户界面公开上游成本、利润或导入数据。

### 4.1 成本身份冲突

232 条成本行落入 77 个现有成本业务键：

```text
channel + billable_upstream_model
```

其中：

- 60 个业务键只有一种真实成本，可使用现有语义；
- 17 个业务键存在多种成本，现有业务键无法无损表达；
- 25 个业务键同时关联多个 SKU；
- 100 个 `channel + upstream model + SKU` 组合同时有 `no_video` 和 `with_video` 行，且两种场景成本完全相同；
- 13 个 `channel + upstream model + SKU` 组合在同一场景仍有重复报价，其中 18 组场景报价不同。

因此，视频场景不是当前成本冲突的主要原因。主要原因是同一个渠道代码和上游模型下混入了不同清晰度、计费方式、真人能力、区域、协议、账户或商务线路。

17 个业务键进一步分为：

- 12 个纯 SKU/清晰度结构冲突：SKU 字段已经提供权威清晰度，转换器可以自动生成不同成本变体和路由目标；
- 3 个 Secure 渠道线路冲突：`CH-SECURE` 的三个上游模型键可以按已确认的 `discount`、`overseas`、`enterprise` 分组契约自动拆成三个渠道；
- 1 个能力变体冲突：`CH-MEGABYAI / videos-standard` 的同一 SKU 因真人能力不同而有不同价格，需要管理员把备注信息确认为结构化能力条件；
- 1 个 MegaByAI 账户能力冲突：`CH-MEGABYAI / videos-fast` 已确认由“不卡脸”和“卡脸”两个独立账号/API Key 产生，可以按真人能力拆成两个渠道线路。

因此，17 个键都是兼容性检测结果，但只有 `CH-MEGABYAI / videos-standard` 仍需要人工决策。其余 16 个在成本变体、Secure 分组和 MegaByAI fast 账户能力映射可用后自动结构化转换。

### 4.2 v1 规范化基准

当前 v1 文件完成 R102-R105 修正后应产生：

- 9 个渠道主数据项；
- 12 个渠道线路候选，其中 `CH-SECURE` 展开为特价、海外和企业三条线路，MegaByAI `videos-fast` 展开为不卡脸和卡脸两条线路；
- 9 个 SKU；
- 16 个用户售价提案；
- 121 个成本草稿候选：先合并相同的 `no_video/with_video`，再排除 4 条 Secure fast/mini 480p 不支持记录；
- 121 个模型映射候选；
- 17 个被检测的现有成本业务键，其中 16 个自动结构化转换、1 个进入人工处理。

上述数量作为固定回归样本。转换器不得为了让导入通过而静默删除冲突成本。

## 5. 已确认的业务决策

1. Excel 只在浏览器本地处理，永远不上传到 new-api。
2. 转换器是纯前端静态网页，并提供详细预览和 JSON 下载。
3. new-api 使用上传、校验、渠道绑定、惰性配置生成、审核、发布的分阶段流程。
4. 新渠道默认禁用。
5. 新路由策略和路由目标默认禁用。
6. 重复导入必须幂等，变化内容必须版本化。
7. 活动配置和历史账本不能被导入器直接覆盖。
8. 官方售价只生成用户售价提案，审核后才能发布。
9. 渠道绑定和渠道创建在 new-api 向导中完成。
10. Excel、JSON、报告和审计中不出现 API Key。
11. 用户组在向导中选择，`default` 默认勾选。
12. FAIL 阻止整个批次；WARN 允许暂存，但相关行不能发布；PASS 才能生成可发布提案。
13. 发布顺序为成本规则、用户售价、路由启用。
14. 根治成本冲突采用“渠道线路 + 成本变体 + 路由目标绑定成本变体”。
15. 保留 v1 原始文件，新增 v2 模板；v1 冲突通过向导解决，v2 使用结构化字段消除歧义。
16. MegaByAI `videos-fast` 的不卡脸和卡脸分组分别使用独立账号/API Key，导入时创建两个普通渠道，每个渠道只保存一枚密钥并默认禁用。
17. 当前源表 R102-R105 的旧报价必须修正为已确认的人民币按次报价，并同步修正真人能力字段；转换器不得按文件名或行号内置价格覆盖规则。

## 6. 总体架构

```text
Excel v1/v2
  -> 静态转换器
     -> 本地预检
     -> 抽取与规范化
     -> 跨表关联
     -> 已知公式重算
     -> 问题列表
     -> 规范 JSON 下载
  -> new-api JSON 导入
     -> Schema 与业务校验
     -> 渠道线路绑定
     -> 冲突解决
     -> 成本草稿与配置提案
     -> 差异审核
     -> 单事务发布
```

系统分成四个边界清晰的组件：

1. **Excel 适配器**：只理解版本化模板，不理解 new-api 数据库 ID。
2. **规范 JSON 契约**：作为转换器和 new-api 之间唯一接口。
3. **导入编排器**：负责校验、绑定、幂等、冲突、暂存和发布。
4. **成本变体核心**：扩展现有成本规则和路由目标，保证运行时选中唯一成本规则。

## 7. 核心术语

### 7.1 渠道主数据

渠道主数据表示供应商或商务主体，包括币种、兑换比例、手续费和来源信息。它不是 new-api 中具体的密钥记录。

### 7.2 渠道线路

渠道线路表示一个可以绑定到具体 new-api 渠道的运行实例，例如不同账号、区域、Base URL、协议或商务合同。线路只保存非敏感引用；API Key 和实际连接配置由管理员在 new-api 向导中填写。

### 7.3 成本变体

成本变体表示同一渠道线路和实际上游模型下的一份独立价格合同。稳定标识为 `cost_variant_key`。

`cost_variant_key` 使用小写 ASCII，格式为：

```text
[a-z0-9][a-z0-9._-]{0,63}
```

旧规则和无需区分的规则使用 `default`。

### 7.4 路由目标

路由目标绑定：

```text
channel line
+ upstream model
+ cost variant key
+ routing constraints
```

请求路由选中目标时，同时确定实际渠道、实际上游模型和成本变体。成本系统不再实现另一套独立的请求条件匹配器。

## 8. v2 Excel 模板

原始 v1 文件保持不变。v2 模板在现有结构上增加结构化线路和路由字段。

### 8.1 工作表映射

| Excel v2 工作表 | 规范 JSON | new-api 结果 |
| --- | --- | --- |
| `渠道` | `channels` | 供应商商务主数据 |
| `渠道线路` | `channel_lines` | 已有渠道绑定或禁用的新渠道候选 |
| `模型SKU` | `model_skus` | 计量规格和路由规格 |
| `官方售价` | `sale_proposals` | 用户售价提案 |
| `渠道成本` | `cost_rule_drafts` | 版本化成本草稿候选 |
| `路由目标` | `route_blueprints` | 路由策略和目标提案 |
| `模型映射` | `model_mappings` | 客户端模型、渠道能力和上游模型映射 |
| `来源` | `sources` | 来源审计 |
| `利润测算`、`校验`、`参数` | `derived_preview`、`issues` | 预览，不作为发布依据 |

### 8.2 渠道线路字段

`渠道线路` 至少包含：

| 字段 | 含义 |
| --- | --- |
| `line_ref` | 模板内稳定线路 ID |
| `channel_ref` | 所属渠道主数据 ID |
| `display_name` | 线路显示名 |
| `provider_type_hint` | new-api 渠道类型提示 |
| `region` | 区域标签 |
| `protocol` | 协议标签 |
| `supports_real_person` | 可选的账号级真人能力约束；填写后，线路下所有路由目标必须一致 |
| `status_proposal` | 固定为 `disabled` |
| `source_ref` | 来源记录 |
| `note` | 仅审计，不参与自动路由 |

线路表不包含 API Key、Authorization、Cookie 或密钥参数。Base URL 和其他运行连接配置在向导中确认。

### 8.3 渠道成本新增字段

`渠道成本` 增加：

| 字段 | 含义 |
| --- | --- |
| `line_ref` | 实际商务线路 |
| `cost_variant_key` | 线路内成本变体 |
| `route_target_ref` | 使用该成本的路由目标 |
| `scenario` | 来源场景；只有成本不同时才参与变体拆分 |

成本配置继续使用现有 `free`、`per_request`、`per_duration` 和 `per_token` 契约。原币价格、换算参数和规范化 USD 单价必须完整保留；服务端重算规范化结果。

### 8.4 路由目标字段

`路由目标` 至少包含：

| 字段 | 含义 |
| --- | --- |
| `route_target_ref` | 稳定目标 ID |
| `canonical_model` | new-api 标准模型 |
| `client_model` | Excel 中的客户端模型或别名 |
| `line_ref` | 渠道线路 |
| `upstream_model` | 供应商实际模型名 |
| `sku_ref` | SKU |
| `cost_variant_key` | 成本变体 |
| `output_resolutions` | 支持清晰度 |
| `duration_values` 或 `duration_min/max` | 时长条件 |
| `aspect_ratios` | 比例条件 |
| `input_modes` | 输入模式 |
| `reference_minimums/limits` | 图片、视频、音频引用范围 |
| `supports_real_person` | 真人能力 |
| `priority` | 目标内优先级 |
| `enabled` | 固定默认为 `false` |

这些字段直接映射现有 `pkg/modelrouting` 约束模型。自由文本备注不得成为可发布目标的唯一条件来源。

## 9. v1 兼容规则

v1 适配器只识别当前模板版本的固定表头和列语义。

### 9.1 可自动转换

- 表头、主键和外键完整的行；
- 可通过 SKU 明确推导的清晰度和标准模型；
- `no_video` 与 `with_video` 成本契约完全相同的行；
- 在 `channel + upstream model` 下只有一个成本契约的 60 个业务键；
- 17 个多成本业务键中仅由 SKU/清晰度造成差异的 12 个键，按 SKU 自动生成稳定 `cost_variant_key` 和分辨率路由目标；
- `CH-SECURE` 的三个上游模型键，按已确认 Secure 分组契约自动拆成三个禁用渠道；
- `CH-MEGABYAI / videos-fast` 按已确认的独立账号和真人能力契约自动拆成两个禁用渠道；
- 现有官方售价、来源和模型映射候选。

相同场景成本合并后，来源定位同时保留两个原始成本规则 ID。

### 9.2 必须人工解决

剩余 1 个多成本业务键生成 `unresolved_variants`。管理员只能选择：

1. 拆分成不同渠道线路；
2. 为同一线路建立不同成本变体并绑定结构化路由目标；
3. 将重复或过期报价排除在本批次之外。

如果相同请求条件仍对应不同价格，系统不能自动选择较低价、较高价或最后一行。该数据必须保留 WARN，直到管理员排除或补充可验证的线路差异。

待处理键为 `CH-MEGABYAI / videos-standard`。

v1 备注可以显示给管理员辅助判断，但转换器和服务端不得把备注解析结果当作发布依据。

### 9.3 Secure 分组映射

`CH-SECURE` 不按 `pro`、`fast`、`mini` 创建渠道，而是按 Secure 上游分组创建三个普通 Secure 渠道：

| `line_ref` | `secure_video_group` | 来源成本行 | 允许模型与清晰度 |
| --- | --- | --- | --- |
| `secure-discount` | `discount` | R67-R71 | pro 720p/1080p/4k；fast/mini 720p |
| `secure-overseas` | `overseas` | R72-R75 | pro 720p/1080p；fast/mini 720p |
| `secure-enterprise` | `enterprise` | R66 | 仅 pro 720p |

三个渠道分别保存一枚对应上游 API Key，创建时默认禁用。转换器只生成非敏感线路引用，API Key 和实际渠道配置仍由管理员在 new-api 向导填写。

当前 v1 文件把 R70、R71、R74、R75 同时展开为 480p 和 720p。Secure 已确认 fast/mini 只支持 720p，因此四条 480p 成本和模型映射记录必须排除，不能生成路由目标，也不能仅因表内存在价格而放宽渠道能力。

### 9.4 MegaByAI fast 账户能力映射

`CH-MEGABYAI / videos-fast` 按已确认的上游账号能力创建两个普通 MegaByAI 渠道，而不是在一个渠道内配置多枚 API Key：

| `line_ref` | 显示分组 | 来源成本行 | `supports_real_person` | 人民币按次成本 |
| --- | --- | --- | --- | --- |
| `megabyai-fast-real-person` | 不卡脸 | R102-R103 | `true` | 480p ¥3.000；720p ¥4.000 |
| `megabyai-fast-no-real-person` | 卡脸 | R104-R105 | `false` | 480p ¥1.200；720p ¥1.600 |

源表修正后，R102-R105 的原币单价和真人能力列必须与上表一致。规范化 USD 成本由源表兑换参数公式计算，并由服务端再次重算；转换器不得保留当前旧价格，也不得在代码中按文件名、行号或固定金额覆盖输入。

两条线路分别绑定一枚对应账号的 API Key，创建时默认禁用。本节的自动拆分规则只适用于 `videos-fast`；其他 MegaByAI 模型不能仅凭本次确认自动归入这两条线路。`videos-fast` 路由目标的 `supports_real_person` 必须与线路能力一致。API Key 不进入 Excel、JSON 或审计；由于系统无法从密钥文本推断账号能力，管理员在发布前必须分别确认两枚密钥与线路分组相符，确认结果只记录操作者、线路和时间，不记录密钥。

## 10. 规范 JSON 契约

顶层结构为：

```json
{
  "kind": "new-api.channel-config-import",
  "schema_version": 1,
  "template_version": "1",
  "manifest": {},
  "entities": {},
  "derived_preview": {},
  "issues": []
}
```

### 10.1 Manifest

`manifest` 包含：

- `source_file_name`；
- `source_sha256`；
- `payload_sha256`；
- `generated_at`；
- `converter_version`；
- 各实体数量；
- 模板识别结果。

`payload_sha256` 对规范排序后的权威实体和来源定位求哈希。`generated_at`、文件名、`issues` 和 `derived_preview` 不参与哈希，因此同一权威配置重复转换会得到相同 payload 哈希。服务端仍在每次上传时重新校验，不能复用转换器的问题结论。

### 10.2 Entities

`entities` 包含：

```text
channels
channel_lines
model_skus
sale_proposals
cost_rule_drafts
model_mappings
route_blueprints
sources
unresolved_variants
```

所有实体使用模板业务 ID 和引用，不使用数据库 ID。所有金额、费率、汇率和倍率使用规范 Decimal 字符串，不能使用 JSON 浮点特殊值。

每个实体包含：

- 稳定业务 ID；
- `entity_hash`；
- 来源 ID；
- Excel 工作表、原始行号和原始业务 ID；
- 权威输入字段；
- 必要的审计备注。

### 10.3 Derived Preview

`derived_preview` 可以包含转换器计算的标准 USD 单价、利润和毛利率，但服务端必须忽略其权威性并重新计算。预览差异产生校验问题，不能直接写入配置。

## 11. 静态转换器

转换器使用项目现有 React、TypeScript、Rsbuild 和 i18n 体系构建独立静态产物。它不依赖 new-api 后端，可以在断网环境打开和使用。

### 11.1 处理阶段

1. 文件签名和模板预检；
2. 表、表头和数据区抽取；
3. ID、文本、Decimal、时间和枚举规范化；
4. 渠道、线路、SKU、售价、成本、映射和来源跨表关联；
5. v1 场景成本合并和冲突分组；
6. 已知成本及利润公式重新计算；
7. 生成问题列表、实体哈希和 payload 哈希；
8. 展示结果并下载 JSON。

### 11.2 页面结构

转换完成后提供以下视图：

```text
概览
渠道与线路
模型 SKU
用户售价
渠道成本
模型映射与路由
问题
JSON
```

每个列表都显示原始工作表和行号。问题可以按严重级别、实体类型、渠道、模型和业务 ID 筛选。

FAIL 存在时禁用正式 JSON 下载；可以保留只读问题报告下载。WARN 不阻止 JSON 下载，但 JSON 中对应实体保持不可发布状态。

### 11.3 确定性

相同工作簿和相同转换器版本必须产生：

- 相同实体业务 ID；
- 相同规范字段；
- 相同实体顺序；
- 相同实体哈希；
- 相同 payload 哈希。

## 12. 成本变体核心改造

### 12.1 成本规则业务键

现有业务键：

```text
channel_id + billable_upstream_model
```

扩展为：

```text
channel_id + billable_upstream_model + cost_variant_key
```

版本唯一键扩展为：

```text
channel_id + billable_upstream_model + cost_variant_key + version
```

同一扩展业务键仍只允许一个活动版本。激活新版本时只退休同一成本变体的旧活动版本。

### 12.2 向后兼容

- 现有成本规则迁移为 `cost_variant_key = default`；
- 新建规则缺省时由服务层写入 `default`，不依赖易产生跨库差异的 GORM 布尔或字符串默认标签；
- 现有路由目标迁移为 `cost_variant_key = default`；
- 没有能力路由目标的旧分发路径只查询 `default`；
- 现有 API 可以暂时省略变体字段，响应始终返回规范值。

### 12.3 路由目标绑定

`route_targets` 增加 `cost_variant_key`。选中的目标把变体写入路由审计、请求上下文、成本覆盖候选和 attempt 快照。

严格成本模式下，目标只有在下列条件满足时才能参与发送：

1. 渠道可用；
2. 上游模型可确认；
3. 绑定变体存在唯一活动成本规则；
4. 规则通过适配器成本能力校验。

目标启用前也执行相同覆盖检查。缺失成本变体时不能回退到其他变体或 `default`。

### 12.4 运行时唯一性

路由约束是选择成本变体的唯一条件系统。成本规则本身不再保存另一套分辨率、时长或真人匹配表达式。

同一渠道下条件重叠且优先级相同的启用目标继续由 `modelrouting.ValidatePolicy` 拒绝。条件重叠但优先级不同的目标按既有优先级规则选择，选中目标的成本变体随目标确定。

## 14. 批次状态与工作流

批次状态为：

```text
validating
blocked
binding
staged
ready
publishing
published
publish_failed
```

状态流转：

1. 管理员上传 JSON，进入 `validating`；
2. 存在 FAIL 时进入 `blocked`；
3. 校验通过后进入 `binding`；
4. 完成线路绑定并生成惰性配置后进入 `staged`；
5. 所有待发布项为 PASS 且完成审核后进入 `ready`；
6. 发布时进入 `publishing`；
7. 提交成功进入 `published`；失败进入 `publish_failed`，活动配置不变。

`publish_failed` 可以在修复外部条件并重新验证后重试。已经成功发布的批次不能再次发布。

## 15. 渠道绑定与配置生成

### 15.1 线路绑定

每个 `line_ref` 可以：

- 绑定已有渠道；
- 创建新渠道；
- 跳过。

绑定已有渠道时校验渠道类型、模型能力和商务身份。创建新渠道时状态固定为禁用，管理员在现有渠道表单中填写 Base URL、API Key 和其他敏感配置。

### 15.2 惰性配置

完成绑定后生成：

- 成本规则草稿；
- 用户售价提案；
- 模型映射提案；
- 路由策略和路由目标提案；
- 差异、冲突和覆盖报告。

成本草稿在 `staged` 阶段物化到现有成本规则表，因为 `draft` 不参与运行时。售价和路由在导入表中保持提案，直到发布事务执行。

### 15.3 路由合并

路由策略业务键继续为：

```text
group_name + canonical_model
```

目标用户组在向导中选择，`default` 默认勾选。对于已有策略，导入器提供：

- `merge`：默认，只新增或更新本批次管理的目标，不删除非导入目标；
- `replace proposal`：显示完整删除、新增和修改差异，管理员明确确认后才可发布；
- `skip`：不发布该策略。

新策略和新目标均以禁用状态生成。现有启用策略在审核前不变。

## 16. 用户售价提案

官方售价不会直接写入活动计费配置。服务端根据当前 new-api 支持的售价模式生成提案：

- Token 售价；
- 按次售价；
- 按时长售价；
- 版本化 billing expression 售价。

如果 `no_video` 和 `with_video` 售价不同，提案必须使用能够由权威请求事实判断场景的现有计费模式或版本化 billing expression。缺少权威输入变量时生成 WARN，不能发布。

所有 billing expression 必须：

- 自包含；
- 指定表达式版本；
- 使用允许变量；
- 在服务端重新编译和校验；
- 遵守 `pkg/billingexpr/expr.md` 的归一化和计费安全规则。

售价提案按选中的用户组展开。已存在的售价只生成差异，不在暂存阶段更新。

## 17. 幂等、版本和并发

### 17.1 批次幂等

相同 `payload_sha256` 的再次上传返回已有批次和已有物化结果，不重复创建成本草稿、渠道、售价提案或路由提案。

不同 payload 哈希创建新批次。每个实体使用：

```text
entity_type + business_id + entity_hash
```

与历史导入结果比较，并标记：

- `new`；
- `unchanged`；
- `changed`；
- `conflict`；
- `excluded`。

### 17.2 配置版本

- 成本变化创建同一扩展业务键的新草稿版本；
- 售价变化创建提案，不直接改活动值；
- 路由变化创建 merge 或 replace 差异提案；
- 完全相同的实体标记 `unchanged`；
- 导入来源和实体哈希写入审计关联。

### 17.3 乐观基准检查

进入审核时记录受影响活动规则、售价和路由策略的基准摘要。发布前重新读取；任何对象在审核期间变化时返回 `STALE_BASE_VERSION`，批次回到 `staged` 并要求重新比较。

两个管理员并发发布同一批次时，只允许一个事务成功。

## 18. 校验和问题门禁

### 18.1 严重级别

- `FAIL`：阻止整个批次进入配置生成；
- `WARN`：允许暂存，但受影响实体不能发布；
- `PASS`：允许生成可发布提案，仍需人工审核。

WARN 不能通过简单“忽略警告”变成可发布。管理员必须补充结构化配置、调整售价或路由、重新绑定线路，或者明确排除该实体。

### 18.2 错误代码族

```text
SCHEMA_*
LIMIT_*
SECURITY_*
REFERENCE_*
DUPLICATE_*
COST_*
PRICING_*
ROUTING_*
CHANNEL_*
STALE_*
```

转换器和服务端共享稳定错误代码。例如：

```text
COST_VARIANT_AMBIGUOUS
COST_NORMALIZATION_MISMATCH
ROUTING_TARGET_OVERLAP
CHANNEL_LINE_UNBOUND
PRICING_NEGATIVE_MARGIN
STALE_BASE_VERSION
```

## 19. 服务端重新计算

服务端不信任下列转换器结果：

- 标准 USD 成本；
- Token/秒换算；
- 用户收入；
- 毛利润和毛利率；
- billing expression 编译结果；
- 路由覆盖结论。

服务端使用规范原始输入重新计算，并与 `derived_preview` 比较。任何差异都生成问题。

所有金额和倍率必须：

- 使用 Decimal；
- 为有限数值；
- 满足正数或非负业务约束；
- 遵守现有 quota 饱和、审计和上限规则；
- 不能通过裸 `int` 转换绕过 `common/quota_math.go`。

## 20. 发布事务

发布前再次执行完整校验、成本覆盖检查、售价校验、路由重叠校验和基准版本检查。

所有受影响业务键按稳定顺序排序并加锁。发布在主数据库单一事务中执行：

1. 激活本批次成本规则版本；
2. 应用已审核用户售价；
3. 创建或更新路由策略和目标；
4. 最后设置已审核的路由启用状态；
5. 写入导入发布审计和批次终态。

任一步失败都回滚全部活动配置变化。缓存、渠道内存快照和路由缓存只在事务提交后刷新。

如果缓存刷新失败，数据库提交不回滚，批次保持 `published`。系统增加管理员可见的 `CACHE_REFRESH_PENDING` 问题并只重试缓存重建，不能重复执行发布事务。

## 22. 安全与资源限制

### 22.1 转换器

- 只接受标准 `.xlsx`；
- 拒绝 `.xls`、`.xlsm`、宏、OLE、外部链接和外部数据连接；
- 文件最大 10 MiB；
- 解压后最大 100 MiB；
- 最多 20 张表；
- 每表最多 20,000 行；
- 总权威实体最多 5,000 条；
- 使用浏览器内存，不写 `localStorage` 或 IndexedDB；
- CSP 使用 `connect-src 'none'`；
- 不加载远程脚本、字体、分析或遥测服务；
- 不执行 Excel 公式，只把公式缓存值作为非权威预览；
- 使用 Web Crypto 计算 SHA-256。

### 22.2 JSON 和服务端

- JSON 最大 10 MiB；
- 严格 schema，拒绝未知字段；
- 限制嵌套深度、字符串长度、实体数量和问题数量；
- 拒绝数据库 ID、密钥字段、NaN、Infinity、负价格和非法倍率；
- 检测 API Key、Token、Authorization、Cookie 和 Secret 类字段；
- 来源 URL 去除查询参数和 fragment，避免签名 URL 泄漏；
- 不访问 JSON 内 URL；
- 不执行脚本、Excel 公式或任意表达式；
- 页面展示对所有文本进行转义；
- 只有管理员可访问批次、成本、售价差异和利润信息。

原始上传字节在严格解析和规范化完成后丢弃。数据库保存规范化 item、哈希、问题、绑定、解决决策和物化结果，以支持审计和恢复。

## 23. 数据库兼容与迁移

所有表和索引必须兼容 SQLite、MySQL 5.7.8+ 和 PostgreSQL 9.6+。

迁移要求：

- 使用 GORM 和现有跨库迁移模式；
- JSON 内容存为 `TEXT`；
- 不使用数据库特有 JSON 查询；
- 扩展成本唯一索引时显式迁移旧索引；
- 现有成本规则和路由目标回填 `default`；
- SQLite 使用兼容的加列和索引重建方式；
- 发布锁使用共享 `lockForUpdate`，SQLite 跳过不支持的 `FOR UPDATE`；
- 不依赖部分唯一索引保证单活动版本；
- 批次、item、绑定和问题使用普通主键与跨库兼容组合索引。

## 26. 端到端验收

1. 管理员在断网环境打开转换器并上传已完成 R102-R105 修正的源表。

10. 修改一个价格重新导入时，只生成对应新成本版本或售价差异。
11. 任一发布步骤失败时，活动配置保持发布前状态。
12. Excel、JSON、页面、日志、报告和审计中均不存在 API Key 或其他凭据。

## 27. 分阶段交付

由于本需求同时涉及成本核心、导入编排、管理向导和独立转换器，按依赖关系分五个阶段实施：

### 阶段一：成本变体基础

- 扩展成本规则业务键、缓存、覆盖查询和 attempt 快照；
- 路由目标绑定成本变体；
- 完成三数据库迁移和运行时回归测试。

### 阶段二：导入契约与后端

- 定义 JSON DTO 和严格校验；
- 增加批次、item、绑定和问题模型；
- 实现幂等、暂存、差异和发布事务。

### 阶段三：new-api 管理向导

- 上传、绑定、冲突解决、用户组选择和差异审核；
- 发布前检查、发布结果和进度恢复；
- 完成 i18n 和响应式验证。

### 阶段四：静态转换器与 v2 模板

- 实现 v1/v2 Excel 适配器；
- 实现本地预览、问题列表、确定性 JSON 和安全限制；
- 交付版本化 v2 模板。

### 阶段五：集成与验收

- 使用保留原始备份的修正后源表执行完整导入；
- 验证 12 个 SKU 冲突键、3 个 Secure 分组键和 1 个 MegaByAI fast 分组键自动结构化，并解决剩余 1 个人工处理键；
- 验证发布事务、幂等、运行时路由和成本核算；
- 完成 SQLite、MySQL、PostgreSQL 和浏览器测试矩阵。

每一阶段都可以独立测试，但阶段二依赖阶段一，阶段三和阶段四依赖阶段二的 JSON 契约，阶段五依赖前四阶段。

## 28. 可行性结论

项目基础已经具备版本化成本规则、模型路由约束、用户售价模式、billing expression、管理员权限和跨数据库模型，新增导入链路在技术上可行。

最大风险不是 Excel 解析，而是当前成本业务键无法表示同一上游模型下的多价格线路。通过新增 `cost_variant_key`、把线路绑定放在 new-api 向导、让路由目标确定成本变体，可以消除双重匹配和静默选价风险。

本设计不要求修改当前原始 Excel。当前 v1 文件可以进入兼容导入和人工冲突处理；长期维护使用结构化 v2 模板，从源头消除备注驱动和业务身份混淆。
