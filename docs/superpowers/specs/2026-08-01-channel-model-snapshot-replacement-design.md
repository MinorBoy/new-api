# 渠道模型全量快照替换设计

## 目标

将每次配置导入视为已绑定渠道的权威模型快照。对本次 `sd收录.xlsx` 中出现并完成绑定的渠道，Excel 派生的有效模型集合是唯一当前清单；数据库中存在但快照中不存在的模型视为已下架。

发布必须在提交前明确展示新增、保留和下架模型，并在一个数据库事务中同步渠道声明、能力、模型映射、路由目标和成本规则。历史成本规则与发布审计必须保留。

## 范围

- 配置导入的绑定、暂存、校验、发布与批次详情接口。
- `channels.models`、`abilities`、`channels.model_mapping`。
- 绑定渠道对应的 `route_targets` 和 `channel_model_cost_rules`。
- 配置导入确认页的模型快照差异展示。
- 配置导入绑定表中“一个渠道可对应多条渠道线”的索引迁移。
- 与上述公开响应字段相关的前端类型、i18n 和测试。

不在范围内：

- 删除全局销售价格。相同标准模型可能仍被其他渠道使用。
- 删除历史成本规则、成本核算请求、日志或审计记录。
- 对未绑定或在导入时选择“跳过”的渠道执行下架。
- 修改渠道凭据、渠道类型或渠道启停状态。

## 权威快照定义

每个已绑定渠道的目标模型集合来自该批次所有未排除的 `model_mappings`：

- 上游模型集合：去重后的 `upstream_model`。
- 对外标准模型集合：经 `configImportRuntimeCanonicalModel` 规范化后的 `canonical_model`。
- `channels.models` 的目标值为上述两个集合的并集，去空、去重并按稳定顺序写入。
- `channels.model_mapping` 的目标值只包含本次快照中的标准模型到上游模型映射。旧映射不再合并保留。

同一渠道绑定多条渠道线时，先合并这些渠道线的完整快照，再计算一次差异，避免一条渠道线误删另一条渠道线仍声明的模型。

## 差异与确认

暂存阶段基于绑定渠道当前状态计算：

- `added_models`：目标集合有、当前集合无。
- `retained_models`：目标集合和当前集合均有。
- `removed_models`：当前集合有、目标集合无。

批次详情新增只读的渠道模型快照差异列表，包含渠道 ID、渠道名、渠道线、三个模型列表及数量。确认页必须始终展示该列表；存在下架模型时使用警示样式并列出每个模型名，不以总数替代明细。

快照差异参与基线哈希。暂存后渠道模型或映射变化时，发布继续以 `STALE_BASE_VERSION` 失败关闭，要求重新暂存和确认。

## 发布事务

发布沿用现有 `PublishConfigImportBatch` 事务，并在销售选项、成本规则激活和路由发布完成后执行渠道模型快照替换。对每个渠道：

1. 使用行锁读取渠道。
2. 重新计算目标模型、映射和差异。
3. 将已下架上游模型对应的活动成本规则更新为 `retired`，设置结束时间并保留版本历史。
4. 将该渠道下引用已下架上游模型的活动路由目标设为禁用；不删除路由策略和目标记录。
5. 完整替换 `channels.models` 与 `channels.model_mapping`。
6. 调用现有 `UpdateAbilities(tx)` 以目标模型集合重建能力。
7. 记录缓存刷新键；事务提交后刷新成本覆盖、路由策略和渠道缓存。

任何一步失败必须回滚整个批次，不允许出现渠道声明已删除但路由或成本规则仍活动的部分状态。

## 绑定语义

绑定只验证渠道存在、渠道类型和渠道线能力，不再要求渠道预先声明快照中的新模型。新增模型由确认后的发布事务写入。新建渠道仍保持手动禁用要求，凭据继续由普通渠道表单管理。

旧版 `idx_config_import_binding_channel` 强制一个批次内每个渠道只能绑定一条渠道线，与按渠道合并多条线路的快照语义冲突。迁移在自动建表前幂等删除该旧唯一索引，继续保留 `(batch_id, line_ref)` 唯一约束以及普通渠道查询索引。迁移不改写已有绑定行，SQLite、MySQL 和 PostgreSQL 均通过 GORM Migrator 执行。

## 历史与审计

- 成本规则使用已有 `retired` 状态，不物理删除。
- 路由目标使用 `enabled=false`，不物理删除。
- 现有 `ConfigImportPublishAudit` 继续保存发布前后哈希。
- 批次详情保存并返回模型差异，使管理员能从已发布批次还原当时确认的下架范围。

## 兼容性

- 不新增数据库表或数据库专用 SQL；使用 GORM 幂等删除旧绑定唯一索引，兼容 SQLite、MySQL 和 PostgreSQL。
- 新响应字段为向后兼容的附加字段。
- 旧批次没有差异快照时返回空列表，不影响读取。
- 跳过绑定不触发任何模型删除。

## 回退

代码回退后，已下架模型不会自动恢复。恢复操作使用原批次确认记录：将需要恢复的模型重新加入下一版 `sd收录.xlsx` 并重新导入，发布会重新创建能力、映射和新成本规则版本。历史 `retired` 规则和已禁用路由目标保留，可供人工审计，不应直接改回活动状态绕过导入验证。

## 验证策略

- 后端单元/集成测试覆盖新增、保留、下架、同渠道多渠道线合并、跳过绑定、旧映射移除、能力重建、路由禁用、成本规则退役和事务回滚。
- 测试验证绑定现有渠道时允许快照包含新模型。
- 前端测试覆盖确认页显示全部下架模型、无下架时的稳定空态和超长模型名换行。
- 运行相关 Go 测试、前端测试、类型检查、lint/格式检查、生产构建和 `git diff --check`。
