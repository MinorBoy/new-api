# 分组可扩展路由要求设计

## 1. 背景与目标

当前模型路由已经支持请求级 `routing.require_real_person`，也支持路由目标级 `constraints.supports_real_person`。缺少的是分组级路由要求，导致管理员无法声明“使用某个分组时，所有请求都必须进入支持真人脸的模型候选集”。

本设计增加可扩展的分组路由要求配置，第一期实现 `require_real_person`，并与现有模型路由策略、自动分组、配置导入和管理员配置页面连接起来。

目标：

1. 分组可以声明强制路由能力要求。
2. 分组要求与请求要求合并后再生成路由事实。
3. `group=auto` 时每个实际候选分组独立应用自己的要求。
4. 要求真人脸但缺少可验证路由策略时 fail-closed，禁止回退到普通渠道映射。
5. 配置可以进入模板导入、预览、发布和回滚流程。
6. 未来增加分辨率、输入模式和素材限制时不需要重复设计分组配置结构。

## 2. 已确认的业务语义

### 2.1 生效要求

```text
生效真人脸要求 = 分组要求 OR 请求要求
```

- 分组要求为 `true` 时，客户端不能通过传入 `false` 降级。
- 分组要求为 `false` 或未配置时，客户端仍可通过 `routing.require_real_person=true` 主动要求真人脸。
- 未配置的旧分组按 `false` 处理，保持兼容。
- `GroupGroupRatio` 仍只负责价格倍率，第一期不增加用户分组到使用分组的路由要求覆盖。

### 2.2 自动分组

请求使用 `group=auto` 时，系统按既有自动分组顺序解析实际分组。每个实际分组都独立读取分组路由要求，然后与请求要求合并并执行该分组的模型路由策略。

某个自动分组没有真人脸候选时，继续尝试下一个自动分组；所有分组均无候选时沿用现有无可用渠道错误语义。

### 2.3 Fail-closed

如果分组要求 `require_real_person=true`，但当前模型没有可用的能力路由事实或分组路由策略，系统不能回退到旧的普通渠道映射。显式分组直接判定无兼容路由；自动分组跳过该分组并继续尝试后续分组。

分组未要求真人脸时，旧的无能力路由策略链路保持原有行为。

## 3. 配置模型与运行时

新增可扩展配置对象：

```go
type GroupRoutingRequirements struct {
    RequireRealPerson *bool `json:"require_real_person,omitempty"`
}
```

运行时配置逻辑上是：

```text
map[string]GroupRoutingRequirements
```

键为分组业务名称，不使用数据库 ID。配置挂载在现有 `ratio_setting` 全局配置体系中，并通过新的系统选项 `GroupRoutingRequirements` 持久化和加载。

配置导入中的分组要求实体复用现有无凭据审计合同，包含 `business_id`、`entity_hash`、`source_ref`、`group_name` 和 `requirements`；运行时配置只使用其中的分组名称和要求对象。

要求：

- 服务器使用项目统一的 `common.Marshal` / `common.Unmarshal` 包装函数处理 JSON。
- 分组名必须非空且去除首尾空格。
- `require_real_person` 必须是布尔值。
- 首期对未知字段拒绝保存，避免拼写错误静默失效。
- 配置更新使用现有运行时快照或读写锁，保存成功后后续请求立即读取新值。
- 配置读取不改变路由策略缓存；策略缓存仍只负责分组和模型目标，分组要求在候选评估时读取。

## 4. 路由数据流

请求进入视频路由链路后：

1. 现有中间件解析请求级 `routing.require_real_person`。
2. 渠道选择确定实际使用分组；显式分组直接确定，`auto` 由现有顺序逐项确定。
3. `evaluateGroupRouting(group, model, ...)` 读取该实际分组的 `GroupRoutingRequirements`。
4. 将分组要求与 `FactsInput.RequireRealPerson` 合并，生成最终 `Facts.RequireRealPerson`。
5. 复用现有 `modelrouting.Match`：当最终要求为 `true` 时，只匹配 `constraints.supports_real_person=true` 的目标。
6. 利润门禁、指定渠道校验、渠道亲和、重试路径继续使用已经过滤后的候选集，不能绕过能力过滤。

管理员路由诊断保留最终有效事实和 `MismatchRealPerson` 计数；普通用户只收到现有通用错误，不暴露供应商能力、渠道或策略细节。

## 5. 管理员界面

配置入口位于现有“系统设置 → 模型与分组定价 → 分组倍率”。

- 分组主表增加路由要求摘要状态，不增加一组长期增长的固定列。
- 分组详情抽屉增加“路由要求”区域。
- 第一期开关文案表达“要求路由支持真人脸”，而不是“模型支持真人脸”，避免把分组要求和目标能力混淆。
- 关闭开关等同于不强制要求；客户端仍可通过请求级参数主动要求真人脸。
- 所有新增文案通过前端 i18n，覆盖 `en`、`zh`、`zh-TW`、`fr`、`ja`、`ru`、`vi`。
- 保存失败显示字段级或配置级错误，不能把非法 JSON 写入系统选项。

## 6. 配置导入

模板的 `document.entities` 增加可选 `group_routing_requirements` 节点：

```json
{
  "entities": {
    "group_routing_requirements": [
      {
        "business_id": "group-routing-requirement:真人分组",
        "entity_hash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
        "source_ref": "source:group-routing-requirements",
        "group_name": "真人分组",
        "requirements": {
          "require_real_person": true
        }
      }
    ]
  }
}
```

导入规则：

- 节点缺失表示本批次不修改现有分组路由要求。
- 同一分组重复出现时整批校验失败。
- 分组不存在时发布前失败，不创建隐式分组。
- 已存在分组按业务名称更新。
- 分组路由要求与本批次相关路由策略在同一发布边界内生效；发布失败不得留下半套配置。
- 预览显示新增、变更和保留项，但不显示任何 API Key 或供应商凭据。

路由蓝图增加可选 `group_name` 字段。字段缺失时按 `default` 兼容旧模板；字段存在时，发布和刷新均使用该分组与模型组成的策略键。这样“真人分组 + 模型路由策略”可以在同一导入批次中建立，而不会被错误写入 `default`。

## 7. 测试与验收

### 后端单元测试

- 分组要求和请求要求的四种布尔组合。
- 未配置分组要求时保持旧行为。
- `Match` 对真人脸目标的正反匹配。
- 显式分组、自动分组、指定渠道和重试路径均不能绕过限制。
- 要求真人脸但无路由策略时 fail-closed。
- 配置 JSON 的空分组、重复分组、非法类型和未知字段校验。

### 配置导入测试

- 节点缺失时保留原配置。
- 新增和更新分组要求。
- 重复分组和未知分组拒绝发布。
- 发布失败时配置和路由策略均不部分写入。

### 前端测试

- 分组详情抽屉可以读取、修改和保存真人脸要求。
- 主表摘要与开关状态一致。
- 保存失败时展示错误且保留用户输入。
- 键盘、可访问名称、禁用和加载状态。
- 所有新增 i18n 键在七种语言中存在。

### E2E 验收

使用至少两个 mock 渠道目标：一个支持真人脸，一个不支持真人脸。分别验证：

1. 分组 A 强制真人脸时只选支持目标。
2. 分组 A 无支持目标时显式请求失败。
3. `auto` 在分组 A 无候选后继续尝试分组 B。
4. 普通分组不设置要求时仍兼容旧路由。
5. 任务日志、路由审计和成本核算记录最终实际分组和目标。

## 8. 非目标

- 第一阶段不改变上游供应商的真人脸审核或内容安全策略。
- 第一阶段不自动判断素材是否包含真人脸；只根据请求声明和分组路由要求筛选能力。
- 第一阶段不为每个用户分组增加独立数据库实体。
- 第一阶段不把供应商成本反推为用户售价。
